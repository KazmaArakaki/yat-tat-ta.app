演出を盛ったときの処理落ちを確かめる

優先度：中 状態：完了 2026-10-06

完了 2026-10-06

実機で3回測った。重い場面で描画は最低 78 まで、発火は最大 73ms まで伸びたが、開発者の指は3回とも遅れも抜けも感じなかった。崩れていたのは声の切れ方だけで、声を専用の再生口で鳴らして直した。描画の道具は Core Animation のままで足りる。3回目の数字を基準値にし、演出を足したらそれより悪くならないかを見る。

Debug ビルドに計測モード（-perf）を作り、一番重い連打を本物の処理で再現して、描画、タッチ→発火、途中で切った音を数える。合格の線と、落ちたときの直し方はセッションのページに。

演出を盛ったときの処理落ちを確かめる　処理落ちの確かめ方

概要

手触りの試作で、音を 150ms 遅らせても指は気づかなかった。
差別化の軸を「ずれの小ささ」から「演出を盛っても止まらないこと」へ置き直した。その「止まらない」を確かめる。

  1. a何を盛るか

    花火、粒子、画面の揺れ、BGM と効果音の重なり。演出インフレの終盤に相当する量。

  2. b何を見るか

    描画が 120Hz を保つか、連打したときに音が欠けないか、「タッチ→発火」が軽い状態の 18〜28ms から伸びないか。

  3. c描画の道具

    いまの Core Animation で足りるか、SpriteKit や Metal が要るか。

比べる相手はドパ九九の失敗。描画が毎秒3.8回まで落ち、音が詰まって入力が遅れた（調査レポート：作るときの注意点）。

優先度が中の理由
差別化の軸そのものの確認になる。崩れるなら、描画の道具選びからやり直しになる。
先送りにした理由
盛る演出の中身は題材で変わる。ドリルの花火と電卓の煽りでは、重さの出方が違う。題材を決めてから、その題材の一番重い場面で試す。
2026-10-06 追記：題材は毎食後スクワットに決まった。一番重い場面は、その日最初の連打で連続記録が伸び、同じ1回で DT の節目にも届く、完了連打の最後の1打。目標回数 20 なら、直前の19打の変換の演出がまだ画面に残っている（題材を決める）。2026-10-06 追記：描画の道具は、粒を CAEmitterLayer で出すところから始める。粒の動きを GPU 側で計算するので、1打ごとにメインスレッドの仕事が増えない。足りるかどうかは、実装のあとの実機確認で、節目の札が3枚重なる最後の1打を叩いて見る。「視差効果を減らす」が入っている端末では、粒と画面の揺れを止める（本作りの設計）。2026-10-06 追記（実装後）：札が3枚重なる1打は、連続30日などの記録がないと実機で作れない。確かめるには、記録を仮に入れる開発用の仕組みが要る。それを作るかどうかも、この課題で決める。いまの実機確認では、目標回数100で DT 100 の札が出る1打までを見る（実機での確かめ方）。2026-10-06 追記（画面全体の演出のあと）：演出がさらに重くなった。画面全体の虹の放射線、火の粉、ドパ揃いのリールと金の粒、確定の金属の文字、ねぎらいの金の炎。記録を仮に入れる代わりに、開発用の見本（起動引数 -demo heavy、Debug ビルドだけ）で一番重い画面を出せるようにした。その上で連打して、音と振動が遅れないかを見る。2026-10-06 追記（スクワット隊のあと）：初めて実機で崩れた。スクワット隊を51人まで増やすと、音が乱れ、叩いた返事が遅れるように感じた。人1人は線4本で描き、しゃがむたびに全員の線の形を動かすので、51人で200本を超える。上限を30人にして様子を見る。まだ崩れるなら、奥の列を線の少ない描き方に変える。
