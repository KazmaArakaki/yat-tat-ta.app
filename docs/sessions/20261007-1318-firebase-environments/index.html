Firebase を開発用と本番用に分ける

開発者の注文

firebase-environmentsを進めてください

課題 firebase-environments（優先度：高）。開発用と本番用の Firebase を分け、App Check を入れる。

01 / why now

いまの1つのプロジェクトで困ること

前のセッションでアカウントの削除を実機で試したとき、消えたのは本番のデータベースの記録でした。まだ利用者がいないので、何も困りません。ところが、リリースしたあとに同じ試し方をすると、試すたびに本番のデータベースへ手を入れることになります。ルールの書き間違い1つで、利用者の記録が読めなくなる。

分けるなら、利用者が0人のいまがいちばん安い。利用者が入ってからでは、分ける作業がそのまま記録の引っ越しになるからです。

App Check も同じ理由で、いま入れます。アプリに埋め込む鍵は誰でも取り出せるので、アプリを通さずに Firebase へ大量に問い合わせることはできてしまう。他人の記録が読まれないのはルールが守っていますが、問い合わせの数は費用になって返ってきます。

02 / environments

どちらを本番にするか

いまの yat-tat-ta を開発用に回し、本番を新しく作る手も考えました。名前の見た目は、そのほうがすっきりします。とはいえ、App Store Connect に入れたプライバシーポリシーとサポートの URL（yat-tat-ta.web.app）は、いまのプロジェクトの Hosting に結びついています。本番を作り直すと、この URL ごと引っ越すことになる。

そこで、いまの yat-tat-ta を本番に残し、開発用の yat-tat-ta-dev を新しく作ります。プロジェクトの ID は Firebase の全体で重ならない名前に限られるので、取れなければ Firebase が付ける末尾の文字ごと使います。

表1　開発用と本番用
項目開発用本番用
Firebase のプロジェクトyat-tat-ta-dev（新しく作る）yat-tat-ta（いまのもの）
使うビルドDebug（Xcode の Run）Release（TestFlight、App Store）
設定ファイルios/Firebase/Dev/GoogleService-Info.plistios/Firebase/Prod/GoogleService-Info.plist
App Checkデバッグ用のトークン。端末ごとに Firebase に登録するApp Attest。本物のアプリかを Apple が確かめる
Firestore のルール本番と同じものを反映するいまのもの
公開ページ（Hosting）使わないyat-tat-ta.web.app（App Store Connect に入れた URL）
入っている記録開発者の試し打ち。消してよい利用者の記録

TestFlight で配るビルドは Release なので、本番に書きます。リリースの前に試してもらう人の記録も、そのまま本番に残ります。

03 / app check

App Check で断るもの

App Check を入れると、Firestore は本物の Yat Tat Ta から来た問い合わせだけを受け付けます。本物かどうかは、Release では App Attest で Apple が確かめます。シミュレーターでは App Attest が動かないので、Debug ではデバッグ用のトークンを使います。トークンは端末ごとに1つ出るので、Firebase の画面に登録します。

断り始めるのは、両方のプロジェクトで最初からにします。古いアプリがまだ出回っていないので、断っても困る人がいません。開発用でも断らせておけば、トークンの登録を忘れたときにすぐ気付けて、本番で初めてつまずくことがない。

Authentication（Apple のログイン）には、今回は App Check をかけません。ログインの問い合わせは Apple の証明書がないと通らず、Firestore ほど数で費用がかさまないからです。

04 / decisions

決めたこと

  • 決定　本番はいまの yat-tat-ta、開発用に yat-tat-ta-dev を作る。Hosting の URL を変えないため（開発者がレビューで合意、2026-10-07）。
  • 決定　Debug は開発用、Release は本番用。設定ファイルはビルドの途中でアプリへ写す。
  • 決定　App Check は Release が App Attest、Debug がデバッグ用のトークン。両方のプロジェクトで、Firestore への問い合わせを最初から断らせる。Authentication にはかけない。
  • 決定　Apple のログインは、本番と同じ Services ID と鍵を開発用でも使う。Services ID に開発用のドメインを足すだけで済む。
  • 決定　firebase deploy は毎回 -P dev か -P prod を付ける。既定のプロジェクトは置かない。

05 / implementation

作るもの

本番のデータベースの記録には触れません。開発用のデータベースは空から始めます。

  1. 1. GoogleService-Info.plist を YatTatTa/ から外し、ios/Firebase/Dev/ と ios/Firebase/Prod/ に置く。どちらも Git に入れない
    YatTatTa/ の中に置くと、xcodegen が両方をアプリに入れてしまう。本番のアプリに開発用のプロジェクトの名前を残さない。
  2. 2. project.yml の Debug と Release に FIREBASE_ENV（Dev か Prod）を設け、ビルドの途中でその設定ファイルをアプリへ写すスクリプトを足す
    Swift のコードに切り替えを書かずに済む。写す元と先をスクリプトの入出力に書いておけば、Xcode のスクリプトの制限（sandbox）の中でも動く。
  3. 3. SDK に FirebaseAppCheck を足し、FirebaseApp.configure() の前に、Release は App Attest、Debug はデバッグ用の仕組みを選ぶ
    App Check は、Firebase につなぐ前に選んでおく決まり。シミュレーターでは App Attest が動かないので、Debug はデバッグ用にする。
  4. 4. App Attest の entitlement（com.apple.developer.devicecheck.appattest-environment）を足す
    本物のアプリかを Apple に確かめてもらうのに要る。
  5. 5. firebase/.firebaserc に dev と prod の名前を付け、既定のプロジェクトをなくす
    firebase deploy を付け忘れのまま打つと、エラーで止まる。開発用のつもりで本番のルールを書き換える事故を防ぐ。
  6. 6. テスト：Release と Debug で写す設定ファイルを取り違えていないかを、ビルドの設定から確かめる
    テストはアプリの外から Firebase に触れないので、確かめられるのは設定まで。取り違えると、開発の試し打ちが利用者の記録に混ざる。
  7. 7. 開発者が実機で確かめる：Debug で叩くと開発用に、TestFlight（Release）で叩くと本番に記録が入る。Firebase の App Check の画面で、問い合わせが「確認済み」になる
    App Attest は実機の Release でしか動かない。シミュレーターでは確かめられない。

06 / developer

開発者にお願いすること（約30分）

Firebase と Apple Developer の画面での作業です。手順はFirebase の準備と運用に書きました。

  1. 1　約10分

    Firebase で開発用のプロジェクト yat-tat-ta-dev を作り、iOS アプリ（com.yat-tat-ta）を登録する。Google アナリティクスは入れない。

  2. 2　約5分

    Firestore を東京（asia-northeast1）に本番モードで作る。

  3. 3　約5分

    Authentication で Apple を有効にし、本番と同じ Services ID と鍵を入れる。Apple Developer の Services ID の設定に、開発用のドメインと Return URL を足す。

  4. 4　約3分

    設定ファイルを2つ置く。開発用は ios/Firebase/Dev/、いまの本番用は ios/YatTatTa/ から ios/Firebase/Prod/ へ移す。

  5. 5　約5分

    両方のプロジェクトの App Check で、iOS アプリに App Attest を登録する。Apple Developer で App ID に App Attest を足す。

07 / build

作ったところ

  • 本番用の設定ファイルを ios/Firebase/Prod/ へ移し、開発者が開発用を ios/Firebase/Dev/ に置いた。project.yml の FIREBASE_ENV（Debug は Dev、Release は Prod）で、ビルドの最後にアプリへ写す。ファイルがなければ、置き場所を書いたエラーで止まる。
  • App Check は AppCheckSetup で選ぶ。Release は App Attest、Debug はデバッグ用のトークン。entitlement に App Attest（production）を足した。テストを1つ足し（Debug のビルドに本番のプロジェクトの設定が入っていたら落ちる）、全88個が通る。Release のビルドに本番の設定が入ることも確かめた。
  • firebase/.firebaserc に dev と prod を置き、既定のプロジェクトをなくした。
  • 開発用のプロジェクトに iOS アプリを登録するとき、一度 Services ID のバンドル ID（com.yat-tat-ta.signin）で登録してしまい、com.yat-tat-ta で登録し直した。
  • 開発用の Firestore を作る前にルールを反映したら、firebase-tools が米国（nam5）にデータベースを作った。空だったので開発者の合意を得て消し、東京に作り直した。同じ名前で作り直せるまで約5分かかった。firebase.json に置き場所（asia-northeast1）を書いて、二度と起きないようにした。
  • 開発者が、両方のプロジェクトで App Check の Firestore を「適用」にし、実機の Debug ビルドで叩いた記録が開発用の yat-tat-ta-dev に入り、本番の yat-tat-ta には入らないことを確かめた（2026-10-07）。
  • TestFlight に 1.0 (1) を出し、Release の App Attest を通って本番の yat-tat-ta に記録が入ること、App Check の画面で問い合わせが「確認済み」になることを開発者が確かめた（2026-10-07）。アーカイブのアップロードでは、Firebase のビルド済みの部品（FirebaseFirestoreInternal、grpc など）に dSYM がないという警告が5つ出たが、アップロードは通った。クラッシュレポートで、その部品の中の行番号が読めないだけ。
