演出を盛ったときの処理落ちを確かめる

このセッションで作るもの（レビュー済み）

計測モード -perf

一番重い連打を、本物の処理のまま、何度でも作れるようにする。
叩いている間の描画、タッチから発火まで、途中で切った音を数え、最後に1枚の札で見せる。
記録は端末に保存しない。

01 / position

「止まらない」は、まだ誰も測っていない

手触りの試作で、差別化の軸を「演出を盛っても止まらないこと」に置き直しました。それから本作りで、演出は試作の何倍にも増えています。スクワット隊、ドパドパの3段階、画面全体の放射線、フィーバータイム、ドパ突破、筋肉確定、ねぎらいの金の炎。

崩れた記録は1つだけあります。スクワット隊を51人に増やしたとき、音が乱れ、叩いた返事が遅れた。上限を30人にして、そのあとは指の感覚で「大丈夫そう」と見てきました。30人なら大丈夫なのか、どこまで余裕があるのかは、数字では分かっていません。

このセッションは、機能を足しません。4つの機能のうち完了連打の演出を、外から測る道具を作ります。作るものはすべて Debug ビルドの中だけにあり、ストアに出すアプリには入りません。

02 / heaviest

一番重い連打は、どう作ればいいのか

いまある見本 -demo heavy は、一番重い画面を出せます。ただ、作り物のフィナーレを置くだけです。札3枚もねぎらいも、叩いた結果として出てくるわけではありません。測りたいのは、30人がしゃがみ、段階が上がり、最後の1打で節目が3つ重なる、その連打そのものです。

そこで、記録のほうを用意します。計測モードで起動すると、端末の記録は読まず、メモリの中だけに仮の記録を入れて始めます。仮の記録は、目標回数100を叩き切った最後の1打で、次の3つが同時に起きるように組みます。

  • 連続記録

    30日目

    昨日まで29日続き、今日はまだ。

  • DT

    1,000 突破

    900 から始める。最後の1打で金のドパ突破。

  • DPW

    ベスト更新

    直近7日の合計が、最後の1打でベストを越える。

途中も重くします。60打目で隊が30人そろい、50打目でフィーバータイムが必ず当たるよう、くじを固定します。フィーバーの10秒は画面全体を叩くので、その間も測ります。100打とフィーバーで、30秒ほどの連打になります。

本作りのころは「記録を仮に入れる仕組み」を作らず、見本で代えました。端末の記録に混ざるのが怖かったからです。今回はメモリの中だけに入れ、アプリを終えれば消えます。端末に保存された記録には、読むことも書くことも一切しません。

03 / measure

指の代わりに、何を数えるか

Claude には、音の遅れも振動の抜けも感じ取れません。手触りの試作と同じく、最後に決めるのは開発者の指です。ただ、指が「なんか重い」と言ったとき、どこが重いのかまでは指では分かりません。数えるのは3つです。

1描画

1秒ごとの描画の回数と、50ms 以上止まった回数。画面の書き換えの合図（CADisplayLink）を受けて数えます。

2タッチ→発火

指が触れた時刻から、音、振動、光の命令を出し終えるまで。試作で測ったものと同じ定義で、軽い状態では 18〜28ms でした。

3途中で切った音

鳴り終わる前に、次の音に場所を譲った音の数と名前。

3つめは、測る前から怪しいと見ています。音は8つの再生口を順番に使い回していて、次の音が来ると、前の音がまだ鳴っていても止めて上書きします。1秒に10回叩けば、同じ再生口には0.8秒で戻ってくる。「激熱！」の声が1秒あれば、言い終わる前に叩いた音に切られます。51人のときの「音が乱れた」の正体は、描画の重さではなく、こちらだったのかもしれません。

1の描画には、数えきれない分があります。CADisplayLink が見ているのはアプリの側の詰まりです。放射線や粒のように、画面を合成する側（render server）が重くて飛んだコマは、アプリの中からは見えません。そこで、札の数字がきれいなのに指が重いと言ったときだけ、Instruments の Animation Hitches で同じ連打を録ります。

04 / mock

計測の札の修正イメージ

叩いている間は左上に小さく出し、指の届く場所をふさがない。ねぎらいが終わったら、まとめの札に変える。アプリの色とは混ぜず、開発用と一目で分かる黒にする。

数字は見本。緑は合格の線の内側、黄は線の近く、赤は外側。

05 / criteria

どこまでなら「止まっていない」と言えるか

線は、試作の数字とドパ九九の崩れ方から引きました。ドパ九九は描画が毎秒3.8回まで落ちています。そこまで行かなくても、50ms 止まれば指は引っかかりを感じやすい。iPhone 15 Pro を、低電力モードを切った状態で測ります。

数えるもの合格線の理由
描画1秒の最低が 100 以上、50ms 以上の詰まりが 0 回120Hz の端末で、1割落ちまでは目に見えにくい。50ms は3コマ分の空白
タッチ→発火最大 40ms 以下軽い状態の上限 28ms に、1コマ（8ms）と少しの余裕
途中で切った音声は 0 回叩いた音どうしが切り合うのは連打の音として聞こえる。声が切れると言葉が欠ける
開発者の指遅れも抜けも感じない最後はこれで決める

06 / branches

落ちたら、どこを直すか

  • 全部合格：描画の道具は Core Animation のままで足りる。課題を完了にする。演出を足したら、このモードで測り直す。
  • 声を切っている：声だけ別の再生口に分け、叩いた音に上書きされないようにする。このセッションの中で直す（30分ほど）。
  • 発火が遅い、アプリ側の詰まりがある：叩いた1打で何が重いかを Instruments の Time Profiler で見る。まず疑うのは、30人の線の形をまとめて動かすところ。奥の列を線の少ない描き方に変える案がある。
  • 札の数字はきれいで、指が重い：合成する側の詰まり。Animation Hitches で録り、重なる全画面の層（放射線、粒、炎）を減らす。それでも足りなければ SpriteKit か Metal を検討する。ここは新しい課題に分ける。

07 / implementation

実装でやること

すべて #if DEBUG の中。所要はあわせて2時間ほど。

  1. 1
    起動引数 -perf で、メモリだけの保存先に切り替える（YatTatTaApp.swift）。叩いた記録で端末の本当の記録を汚さないため。
  2. 2
    仮の記録を入れる（新規 Mash/PerfSeed.swift）。29日の連続、DT 900、DPW がベストの手前。目標回数は100。最後の1打で節目が3つ重なる状態を、見本ではなく本物の処理で作るため。テストで「100打目に3つ重なる」を確かめる。
  3. 3
    フィーバーのくじを50打目で当てる。いまの draw を差し替える。0.51% のくじを待たずに、毎回同じ重さで測るため。
  4. 4
    3つを数える（新規 Perf/PerfMonitor.swift）。描画は CADisplayLink、発火は叩く面とフィーバーの面の touchesBegan の終わりで、切った音は FeelEngine の再生口ごとに鳴り終わる時刻を覚えて数える。
  5. 5
    計測の札を出す（新規 Perf/PerfHUD.swift）。数字を開発者がそのまま読めて、写真1枚で Claude に渡せるようにするため。「もう1回」で仮の記録を入れ直す。

データベースの形は変えない。端末に保存された記録には触れない。

08 / steps

実機での確かめ方（開発者、10分）

  1. 1Xcode の Scheme の Arguments に -perf を足し、iPhone 15 Pro に入れる（低電力モードは切る）
  2. 2100打を全力で叩き切る。50打目からのフィーバーは画面全体を叩き続ける
  3. 3まとめの札をスクリーンショットする。「もう1回」で、あと2回繰り返す
  4. 43枚の写真と、「指で遅れや抜けを感じたか」を一言で Claude に渡す

09 / decisions

決めたこと（2026-10-06 開発者がレビュー）

  1. 01処理落ちは、Debug ビルドの計測モード（-perf）で確かめる。
  2. 02計測モードは、メモリだけの保存先に仮の記録を入れて始める。端末の記録には触れない。
  3. 03測る場面は、目標回数100、30人、50打目のフィーバー、最後の1打で節目3つ（30日、DT 1,000、DPW ベスト）。
  4. 04数えるのは、描画、タッチ→発火、途中で切った音。合格の線は 05 の表のとおり。
  5. 05演出を足したり重くしたりしたら、計測モードで測り直す（devops／処理落ちの確かめ方）。
