02 / questions

確かめたいのは3つ

前々回の調査で、差別化の本体を「タップ→音→振動→光の4つがずれずにそろう手触り」に置きました。Swift を選んだのもそのためです。ところが、どれくらいのずれなら人は気づくのか、その数字はまだ誰も手にしていません。

しかも、Claude には振動も音の遅れも感じ取れません。数字の一部はアプリの中で測れても、最後に決めるのは開発者の指です。だから試作は、指で比べられる形にしました。

  1. Q1

    A と B、どちらがそろって感じるか

    音と振動を別々の仕組みで鳴らすか、1つの仕組みでまとめて鳴らすか。

  2. Q2

    音を何 ms 遅らせると気づくか

    気づき始める値が、守るべき同期ずれの上限になる。

  3. Q3

    連打で強くなるのは気持ちいいか

    0.45秒以内に叩き続けると8段階まで上がる。演出インフレの、ごく小さい味見。

  1. 上段：計測値

    「タッチ→発火」は、指が触れた時刻から音・振動・光の命令を出し終えるまで。iOS がタッチをアプリに届けるまでの時間も含む（実機で 18〜28ms）。「音の出力遅延」は iOS が申告する出力バッファと出力経路の遅れの合計です。どちらも、手に届くまでの全部ではありません。

  2. 中央：叩く面

    指を離したときではなく、触れたときに鳴ります。複数の指で同時に叩いても、1本ずつ鳴ります。

  3. 音・振動・光

    1つずつ切れます。光だけ消して叩くと、音と振動がどれだけ「叩いた感じ」を背負っているかが分かります。

  4. A 別々 ／ B 一体

    Q1 の切り替え。中身は 04 しくみ。

  5. 音をわざと遅らせる

    Q2 のつまみ。0〜150ms を 10ms 刻みで。振動と光はそのままで、音だけが遅れます。

04 / how

しくみ

調査の段階では、音は AVAudioEngine、振動は Core Haptics と、別々の仕組みで鳴らすつもりでした。それぞれ遅れを抑えやすい道具だからです。ただ、別々の仕組みは、別々の時計で動きます。2つの遅れが同じ大きさだという保証はありません。

Core Haptics には、振動と一緒に音のファイルを鳴らす機能があります。1つのパターンの中に置けば、同じ時計で並べてくれるはずです。はず、でしかないので、両方を作って切り替えられるようにしました。

ずれを生まないための選択

どれも、タップの瞬間にやる仕事を減らすか、待ち時間を短くするためのものです。

選んだこと理由
UIKit の touchesBegan で受けるSwiftUI のボタンは指を離したときに反応する。触れた瞬間を、間に何も挟まずに受け取りたい。
音は起動時に8段階ぶん合成しておく叩くたびに作ると、その分だけ遅れる。外部の音素材も持たない（ドパ〇〇の事例と同じ）。
振動のプレイヤーも先に作っておく同じ理由。B のパターンだけは、ON/OFF と遅らせ幅を変えたときに作り直す。
音のプレイヤーを4つ順番に使う1つだと、連打したときに前の音が途中で切れる。
画面を 120Hz で描くiPhone 15 Pro は 120Hz で描けるが、設定しないとアニメーションは 60Hz に絞られる。光が出るまでの待ちが最大約17ms から約8ms に縮む。
面全体の光は弱く、輪は指の位置だけ連打で画面全体が強く明滅すると、光過敏の人に負担になる（ひかえめモードの考え方）。

「音をわざと遅らせる」は、A では音の再生時刻を指定し、B ではパターンの中で音の開始時刻をずらしています。どちらも時刻指定なので、遅らせ幅そのものはぶれません。

05 / steps

実機での確かめ方

開発者の作業です。全部で15分ほど。音が出るので、イヤホンなしで静かな場所が向いています。2026-10-06 に、この手順で実施しました。

  1. 1cd ios && xcodegen generate を実行し、Xcode で iPhone 15 Pro に入れる（2分）
  2. 2上段の「振動」が「動作中」になっていることを見る。違えば表示をそのまま Claude に伝える
  3. 3Q1：A と B を切り替えながら、1回ずつゆっくり叩く。そろって感じるほうを選ぶ（5分）
  4. 4Q2：Q1 で選んだほうで、つまみを 0ms から 10ms ずつ上げる。「音が遅れた」と感じた最初の値を覚える（5分）
  5. 5Q3：つまみを 0ms に戻して連打し、気持ちいいかを一言で。上段の「タッチ→発火」と「音の出力遅延」の値も添えて Claude に伝える（3分）

06 / results

実機での結果

数十 ms のずれなら、さすがに気づくだろうと思っていました。音と触覚のずれは、そのあたりから気づく人が多いとされているからです。

問い開発者の判定
Q1 A と B違いが分からない
Q2 音を遅らせる150ms（つまみの最大）でも気づかない。ゆっくり叩いても、連打してリズムを見ても、崩れて感じない
Q3 連打気持ちいい
計測値（0ms）タッチ→発火 18〜28ms ／ 音の出力遅延 20.8ms

Q2 の答えを聞いて、最初に疑ったのはつまみのほうでした。遅らせる処理が効いていないのかもしれない。そこでシミュレーターで A を使い、叩いてから音が鳴り終わるまでを3回ずつ測りました。0ms では 188／208／199ms、150ms では 344／341／341ms。差は約140ms で、ほぼ設定どおりに遅れていました。

つまり、遅れは本当に出ていて、指がそれを拾わなかったことになります。

調査のときの見込み

ずれの小ささを売りにする

4つが ms 単位でそろうことが、Web にはないネイティブの強み。

置き直した見込み

盛っても止まらない

150ms を拾えない指でも、入力が詰まる、描画が飛ぶ、は分かる。

見直してみると、調査で拾った Web の失敗例も ms 単位のずれではありませんでした。ドパ九九は描画が毎秒3.8回まで落ち、音が詰まって入力が遅れています。指が気づくのは、ああいう崩れ方のほうです。ネイティブで守る価値があるのは、演出を盛ったときにもタップへの返事が途切れないこと。ただし今回の面には、盛った演出がまだ1つもありません。そこを確かめるのは課題 heavy-effects-performance です。

  • 判定したのは開発者1人、端末は iPhone 15 Pro だけ。ずれに敏感な人なら気づく可能性は残る。
  • 「タッチ→発火」の 18〜28ms は、iOS がタッチを届けるまでの時間を含む。アプリの処理だけを切り出した値ではない。
  • 耳に届くまでの合計は、2つの計測値を足しておよそ 40〜50ms と見積もれる。スピーカーそのものの遅れは含まない。

07 / decisions

決めたこと

  1. 01試作は題材を持たない。叩く面が1枚だけの画面にする。題材が決まるまで、アプリを起動するとこの画面が出る。
  2. 02音と振動の鳴らし方は A 別々 と B 一体 の2通りを作り、実機で比べて決める。
  3. 03タップは指が触れた瞬間に受ける。離したときではない。
  4. 04画面は 120Hz で描く。INFOPLIST_KEY_ で書けないキーなので、ios/YatTatTa/Info.plist を置いて生成分とマージする（iOS プロジェクトの設定に追記）。
  5. 05試作ではマナーモードでも音を鳴らす。本作りでどうするかは課題 silent-mode-sound で決める。
  6. 06本作りの音と振動は A 別々 で鳴らす。B と違いが分からなかったので、仕組みが単純なほうを取る。B のように音をファイルに書き出して登録する手間がない。
  7. 07差別化の軸を「ずれの小ささ」から「演出を盛っても止まらないこと」へ置き直す。確かめ方は課題 heavy-effects-performance で決める。

08 / deferred

先送りにしたこと

  • マナーモードで音を鳴らすか

    試作で「音が出ない」と迷わないよう、いまは鳴らしている。電車の中で突然鳴るアプリにしてよいかは、題材が決まってから。課題 silent-mode-sound。

  • 演出を盛ったときの処理落ち

    今回の面は輪が1つ広がるだけで、端末にとっては軽い。花火や粒子を重ねても入力と音が詰まらないかは、まだ分からない。課題 heavy-effects-performance。

  • 手に届くまでのずれの実測（見送り）

    ハイスピード撮影などで、スピーカーと本体の振動の時刻を測る手はある。150ms を指が拾わなかったので、いまは測る理由がない。
