記録を Firestore に移す

開発者の注文

新しいiPhoneに買い換えたら
スクワットの記録は無くなる？

iPhone版が安定したらAndroid版も考えており、今後機能追加する際にデータベースが必要になるかもしれないので、今のリリース前段階でデータベース接続に移行したい。

01 / now

いまの記録が消えるとき

いまの記録は、SwiftData で iPhone の中にだけ置いています。サーバーもアカウントもありません。それでも、たいていの機種変更では残るはずです。クイックスタートでも iCloud バックアップからの復元でも、アプリの中身ごと新しい iPhone へ移るからです。

消えるのは、「新しい iPhone として設定」して App Store から入れ直したときと、アプリを削除したときです。どちらも、利用者の側からは「普通に機種変更しただけ」に見えるかもしれません。

iCloud に同期する手（CloudKit）も考えました。ログインなしで、設定を足すだけで済みます。ただし CloudKit は Apple の端末どうしでしか同期できず、Android 版を出すと記録が分かれる。将来の機能でデータベースが要る可能性もあるので、リリース前のいま、サーバーのデータベースへ移すことにしました（開発者が決定、2026-10-07）。

02 / decisions

決めたこと

  • 決定　データベースは Firestore（Firebase）。iOS と Android の両方に公式の SDK があり、電波がないあいだの書き込みを端末に溜めておける（開発者が決定、2026-10-07）。
  • 決定　最初の起動で Apple でログインしてもらう。ログインしないと叩けない。全員の記録が必ずアカウントに残る（開発者が決定、2026-10-07）。
  • 決定　SwiftData はやめ、Firestore に一本化する。端末側の保存は Firestore のキャッシュに任せる（開発者が決定、2026-10-07）。
  • 決定　いま端末にある記録（開発中のテストデータ）は捨てる。移す処理は作らない（開発者が決定、2026-10-07）。
  • 提案　Apple のボタンは「Appleで続ける」。名前とメールアドレスは求めない。
  • 提案　設定シートにアカウントの欄を足し、ログアウトとアカウントの削除を置く。
  • 提案　端末の設定（目標回数、通知、見せた印）は UserDefaults に残す。サーバーへは移さない。

03 / flow

ログインはどこに入るか

何をするアプリかを見せてからログインを頼む順も考えました。はじめての幕の14秒を先に見せれば、ボタンを押す理由が伝わる。とはいえ、幕はスプラッシュとチュートリアルにつながっていて、あいだにログインを挟むと流れが3つに切れます。

そこで、ログインを一番前に置きます。ログイン画面の一行目は「機種を変えても、記録はそのまま。」です。ボタンを押す理由は、この一行で伝えます。

  1. ログイン画面まだログインしていない人だけ
  2. →
  3. スプラッシュいまどおり
  4. →
  5. はじめての幕端末で1度
  6. →
  7. チュートリアル記録が1件もない人
  8. →
  9. ホーム

Yat Tat Ta

機種を変えても、
記録はそのまま。

Apple でログインすると、記録がアカウントに残ります。

Zzz

Appleで続ける

名前とメールアドレスは受け取りません。

動く見本はページ：はじめの画面（旧ログイン画面）にあります。押すと、寝ていたスクワットマンが起き上がります。

初めてのログインだけは電波が要ります。つながらないときは「電波のあるところで、もう一度」と1行出して待つ。2回目からはログインしたままなので、地下の食堂でも叩けます。

機種変更した人は、ログインするとまず記録が届きます。はじめての幕は端末ごとの印なのでもう一度出ますが、チュートリアルは出ません。記録が1件でもある人には出さない決まりだからです。ただし、記録が届く前にスプラッシュが終わると、記録のある人にもチュートリアルが出てしまう。出すかどうかは、サーバーから最初の答えが返るまで待って決めます。

04 / store

記録の置き場所

記録の形は変えません。完了連打1回で1件、列はいまの SquatRecord と同じ4つです。置き場所だけが、iPhone の中から利用者ごとの棚に変わります。

users/{uid}/records/{recordId}
  startedAt   timestamp   叩き始めた日時
  day         int         記録日（yyyymmdd）。叩き始めた瞬間に決める
  reps        int         ドパに変えたスクワットの回数。1以上
  bonusDopa   int         フィーバータイムで取ったドパ。0以上
  createdAt   timestamp   サーバーが受け取った日時（serverTimestamp）
表1　置き場所の決まり
項目決まり理由
uidFirebase Authentication が Apple のログインに割り当てる番号Apple ID が同じなら、iPhone でも Android でも同じ番号になる
recordId端末で作る UUID電波がなくても、その場で番号が決まる
createdAt新しく足す列。画面には使わないあとで「前回から増えた分だけ読む」ときの目印になる（課題 firestore-read-cost）。足すのはいましか楽にできない
読み書きの権限自分の棚だけ。足すと消すはできるが、書き換えはできない。列と型をルールで確かめる記録はいまも足すか消すだけ。書き換えを許す理由がない
電波がないとき書き込みは端末のキャッシュに入り、画面はすぐ動く。電波が戻ったら送られる食べた直後に、電波を待たせずに叩ける
計算する数DT、DPW、連続記録、休み券はいまどおり記録から計算する。サーバーには置かない計算した数を保存すると記録と食い違う日が来る、というデータベースの方針のまま

05 / arrival

叩いている最中に記録が届いたら

いまは、記録を読み直すのが起動したときと消したときだけです。Firestore では、ほかの端末で叩いた記録や、ログイン直後に届く記録が、いつでも割り込んできます。届くたびに読み直せばいい、と最初は考えました。

ところが、完了連打の途中で読み直すと、DT が一気に跳ねます。節目は叩くたびに「前の DT から今の DT までに閾値をまたいだか」で決めるので、届いた分まで自分の連打の手柄になってしまう。叩いている最中に届いた記録は、連打を閉じてから読み直します。

06 / account

設定シートのアカウントの欄

アカウントを作れるアプリは、アプリの中から削除もできないと App Store の審査を通りません。削除は取り返しがつかないので、確かめる画面を1枚挟み、もう一度 Apple で本人か確かめてから消します。下の見本は、押すと確かめる画面が出ます。

設定

閉じる
目標回数　20 回
今日まだ通知　21:00
使い方をもう一度
NEW

アカウント

Apple でログイン中

削除すると、これまでの記録がすべて消えます。元には戻せません。

膝や腰が痛むとき、医師から運動を止められているときは、休んでください。…

  • Apple でログイン中：誰のアカウントかは出さない。メールアドレスを受け取っていないので、出せるものがない。
  • ログアウト：確かめてから、ログイン画面へ戻る。記録はアカウントに残り、同じ Apple ID でログインすると戻る。端末のキャッシュは消す。
  • アカウントを削除：確かめる、Apple でもう一度本人確認、記録をすべて消す、Apple との連携を切る、アカウントを消す、ログイン画面へ。電波がないと押せない。
  • 叩いている最中：どちらも押せない。「使い方をもう一度」と同じ。

07 / implementation

作るもの

保存の仕組みを入れ替えるので、端末にある記録は消えます。リリース前の開発者の端末だけで、捨てることに合意済みです（2026-10-07）。

  1. 1. project.yml に Firebase の SDK（FirebaseAuth、FirebaseFirestore）を Swift Package で足し、Sign in with Apple の entitlement を足す
    SDK がないと Firestore に触れない。entitlement がないと、Apple のログインの画面が開かない。
  2. 2. SquatRecord を SwiftData の @Model から普通の struct に替え、SwiftData を外す
    一本化すると決めたので、SwiftData を残す理由がない。struct なら Firestore の文書との行き来も、テストで作るのも軽い。
  3. 3. 記録の出し入れを RecordStore（足す、消す、全部消す、変わったら知らせる）にまとめ、Firestore 版とメモリ版を作る
    テストと計測モード（-perf）の仮の記録を、利用者の棚に書かないため。いまの「計測モードはメモリだけの保存先を使う」と同じ考え方。
  4. 4. AppModel を ModelContext から RecordStore に替え、届いた記録で計算し直す。叩いている最中は閉じるまで待つ
    ほかの端末の記録やログイン直後の記録を画面に出すため。待つ理由は05。今日まだ通知の予約も、読み直したら組み直す。
  5. 5. チュートリアルを出すかは、サーバーから最初の答えが返ってから決める
    機種変更した人に、記録が届く前にチュートリアルを出さないため。
  6. 6. ログイン画面と、ログインの状態で画面を切り替える入り口（YatTatTaApp）
    ログインしないと叩けない、と決めたから。ログインしたら、その uid の棚で AppModel を作る。
  7. 7. 設定シートのアカウントの欄。ログアウトと、アカウントの削除（本人確認、記録の削除、Apple との連携を切る、アカウントの削除）
    削除は App Store の審査の条件。Apple との連携を切ることも、Sign in with Apple を使うアプリに求められている。
  8. 8. Firestore のルール（firebase/firestore.rules）を書き、リポジトリに置く
    アプリに埋め込む Firebase の鍵は、誰でも読める。他人の棚を読ませないのはルールの仕事。
  9. 9. 文言を日本語と英語で足し、訳語表にアカウント（Account）、ログイン（Sign in）、ログアウト（Sign out）を足す
    多言語の決まり事で、文言を足すときは2言語同時。
  10. 10. テスト：メモリ版の RecordStore で今の79個を通す。叩いている最中に届いた記録で DT と節目が動かない、閉じたら入る、届いた記録で今日の記録と連続記録が直る
    保存の仕組みを替えても、数の計算が変わっていないことを押さえる。
  11. 11. 開発者が実機で確かめる：ログイン、機内モードで叩いて戻したら届く、アプリを消して入れ直したら戻る、アカウントの削除
    電波と Apple のログインは、シミュレーターでは確かめきれない。

08 / developer

開発者にお願いすること

Firebase と Apple Developer の画面での作業は、開発者のアカウントでしかできません。手順はFirebase の準備と運用にまとめました。実装を始める前に済んでいれば、途中で止まりません。

  1. 1　約10分

    Firebase のプロジェクトを作り、iOS アプリ（com.yat-tat-ta）を登録する。

  2. 2　約5分

    Firestore を東京（asia-northeast1）に作る。

  3. 3　約15分

    Authentication で Apple を有効にし、OAuth コードフローの構成（Services ID と鍵）も登録する（削除のときに連携を切るために要る）。

  4. 4　約2分

    GoogleService-Info.plist を ios/YatTatTa/ に置く。Git には入れない。

09 / later

リリースまでに残ること

サーバーを持ったことで、リリース前に片づける仕事が3つ増えました。どれも今回の実装は止めないので、課題に分けます。

  • privacy-policy

    プライバシーポリシーと、App Store のプライバシーの表示。優先度：高（リリース前に必須）。

  • firebase-environments

    開発用と本番用の Firebase を分ける、App Check を入れる。優先度：高（リリース前）。

  • firestore-read-cost

    起動のたびに全部の記録を読む費用。優先度：低（利用者が増えてから）。

11 / build

作ったところ

  • Firebase の SDK は 12.19 系（FirebaseAuth、FirebaseFirestore）。GoogleService-Info.plist は ios/.gitignore に入れた。
  • SwiftData を外し、記録の出し入れを RecordStore にまとめた。Firestore 版は、届いた記録の顔ぶれ（ID）が変わったときと、サーバーの答えが初めて返ったときだけ知らせる。自分の書き込みが戻ってきた知らせでは、計算し直さない。
  • チュートリアルは、サーバーの答えが返るまで待つ。設計では「電波がなければキャッシュの答えで決める」としていたが、やめた。初めてのログインには電波が要るので、記録が0件のまま電波がない人は、ほぼいない。キャッシュで決めると、機種を替えた人にチュートリアルが出るおそれのほうが大きい。
  • 演出の見本（-demo）も、計測モードと同じくメモリだけの記録で、ログインせずに開く。シミュレーターで Apple のログインを毎回せずに済む。
  • 文言18個を日本語と英語で足し、訳語表に3行足した。ルールは firebase/firestore.rules に置いた。
  • テストを6個足した（RecordSyncTests）。叩いている最中に届いた記録で DT と節目が動かない、届いた記録で今日の記録と連続記録が直る、サーバーの答えを待ってチュートリアルを決める、文書と記録の行き来。全85個が通る。
  • 開発者がルールを反映した（Firebase CLI、2026-10-07）。
  • 実機で、Xcode のビルドが Firebase の部品のダウンロードでつまずいた。コマンドラインのビルドと Xcode が、同じ置き場に同時にダウンロードしたため。Xcode を閉じて置き場（DerivedData の SourcePackages/artifacts）を消し、Reset Package Caches で取り直したら通った。Xcode を開いている間は、コマンドラインでビルドしない。
  • アプリを消して入れ直すと、ログイン画面を出さずにログインしたまま始まった。Firebase がログイン状態を iPhone のキーチェーンに残し、キーチェーンはアプリを消しても残るため。入れ直した人にログインし直してもらう理由がないので、このままにする。新しい iPhone ではキーチェーンが空なので、ログイン画面から入る。
  • 開発者が実機で確かめた（2026-10-07）。ログインして叩いた記録が Firestore に入る。機内モードで叩いた記録は、電波が戻ったら入る。入れ直すと記録が戻る。ログアウトしてログインし直すと記録が戻る。アカウントを削除すると、記録もユーザーも消えてログイン画面に戻る。
